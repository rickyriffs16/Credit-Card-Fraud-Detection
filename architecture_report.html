1 Architectural Overview & Core Objectives

The **Credit Card Fraud Detection System** is engineered as a secure, production-grade 3-Tier application. Its primary design objective is to evaluate transaction data with ultra-low latency (<50ms), maximize fraud detection recall (>84%), and minimize customer disruption through low false-positive rates (<0.1%).

3 Data Pipeline & Sequential Processing Flow

The data pipeline is designed with strict data isolation to eliminate data leakage between train and test distributions:

1. Preprocessing & Scaling Pipeline

Input: Raw 30 features (Time, Amount, V1–V28).
Transformation: StandardScaler is fitted exclusively on training data to scale monetary and temporal variance without leaking test-distribution parameters.

2. Class Imbalance Mitigation (SMOTE)

Challenge: Severe 0.172% fraud class disparity.
Mechanism: Synthetic Minority Over-sampling Technique (SMOTE) generates synthetic mathematical interpolations along k-nearest fraud neighbors to achieve 50:50 class parity in training.

3. Dual-Mode Inference Pipeline

Real-Time Single Scoring: Feature vector → Preprocessor → Random Forest prediction → Sigmoid probability → Risk Category (Low <30%, Medium 30-70%, Critical >70%). Latency: <50ms.
Batch CSV Pipeline: Chunked DataFrame ingestion → Vectorized matrix multiplication → Anomaly flagging → CSV audit report generation.

5 Security Architecture & Database Schema
Authentication & RBAC Architecture
  • Password Security: Salted bcrypt one-way cryptographic hashing.
  • Role-Based Access: Admin (model re-training & user configuration) vs. Analyst (data upload, inference, and audit reporting).
  • Session Preservation: Parent-frame JS bridge bridging localStorage with URL query params.
Database Schema (SQLite: database.db)
  • users: id, username, password_hash, role, created_at.
  • activity_logs: id, user_id, action, details, timestamp.
  • settings: user_id, theme, risk_threshold, updated_at.
